cargo-mutants installation and basic use:
```bash
# Install (if not already installed)
cargo install cargo-mutants

# Verify installation
cargo mutants --version

# Scope to specific files (REQUIRED — do not run on full codebase)
# Use nextest for faster runs, set timeout to skip slow mutants
cargo mutants --file src/cache.rs --test-tool=nextest --timeout 60

# Multiple files at once
cargo mutants --file src/cache.rs --file src/sources.rs --file src/state.rs \
    --test-tool=nextest --timeout 60

# Output: .mutants/ directory (or mutants.out/ depending on version)
# Lists: caught mutants (tests detected), missed mutants (tests didn't detect), timeout mutants
```

Interpreting output:
- **Caught**: Tests detected the mutation — good coverage
- **Missed**: Tests did NOT detect the change — behavioral gap → needs a test
- **Timeout**: Mutation caused an infinite loop or very slow test — usually worth investigating
- **Unviable**: Mutation doesn't compile — not a coverage issue, skip

Anti-pattern: Do NOT run `cargo mutants` without `--file` scope. lib.rs + cli.rs have 15,000+ lines and would take hours.

For each missed mutant, determine:
1. Is it a real behavioral gap? → Write a test that catches it
2. Is it an equivalent mutant (same behavior despite code change)? → Document it

Equivalent mutant documentation format (create if mutants exist):
```
# mutants.out/equivalent-mutants.txt
# Format: <file>:<line> - <mutation> - <reason it's equivalent>
src/cache.rs:105 - replace `>` with `>=` on update check - value never equals threshold in practice
```

**Step 1: Address real gaps**

For each missed mutant that represents a real behavioral gap from Task 1:

1. Understand WHAT behavior the mutant changes (read the source code context around the mutation site)
2. Write a test that specifically exercises that behavior and would fail if the mutation were present
3. Add the test to the appropriate module (unit test in the same file, or integration test in tests/cli.rs for end-to-end behavior)

**Test placement:**
- Mutations in cache.rs → add to `src/cache.rs mod tests` using `make_test_manager()` pattern
- Mutations in sources.rs → add to `src/sources.rs mod tests` (if module has tests) or a new `mod tests` block
- Mutations in state.rs → add to `src/state.rs mod tests` using existing state test patterns
- Mutations in end-to-end paths → add to `tests/cli.rs`

**Key principle:** Each test for a mutant must be SPECIFIC to that behavioral gap. Do not write vague tests hoping they'll catch something.

**Example:** If a mutant deletes the check `if !output.status.success()` in `update_repo`, a test that:
1. Calls a method that triggers `update_repo`
2. Arranges for the git command to fail
3. Asserts the Result is Err

would catch that mutant.

**Step 2: Document equivalent mutants**

For mutants that are equivalent (same behavior despite code change), create the documentation file:

```bash
mkdir -p mutants.out
# Create equivalent-mutants.txt with one entry per equivalent mutant

# These mutations produce identical behavior to the original code in all realistic inputs
#
# Format: <file>:<line> - <mutation description> - <reason it's equivalent>
```

3. Mutations in validation logic (path checks, URL validation)

Cap effort at addressing the top 10-15 highest-impact gaps. Document remaining gaps as "out of scope for this phase" in the SUMMARY.
