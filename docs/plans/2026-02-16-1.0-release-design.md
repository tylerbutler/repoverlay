# repoverlay 1.0 Release Design

## Goals

1.0 means **stable CLI surface** AND **complete core use cases**. After 1.0, the command names, flags, state format, and config format are subject to semver — no more breaking changes without a major version bump.

Primary audience: solo developers managing config overlays across repos. Team/sharing features (e.g. #103) are deferred to post-1.0.

## Current State

- v0.5.0 released, v0.6.0 pending
- 5 open PRs representing significant in-flight work
- 9 open issues ranging from UX polish to new features
- 85 tests, Rust 2024 edition, clippy pedantic+nursery

### Phase 2 — Feature Gaps

New features required for a complete 1.0 experience.

#### Interactive conflict resolution (#35)

Currently `--force` (overwrite all) or `--skip-conflicts` (skip all) are the only conflict strategies. Add `--interactive` that prompts per-file with options: overwrite, skip, diff, merge. Applies to `apply`, `restore`, and `update` commands.

#### Filter in browse/apply list (#76)

When a user has many overlays across many repos, showing all of them is noisy. Add filtering (automatic by current repo's org/repo, or explicit `--filter` flag) to show only relevant overlays.

#### `sync --all` (#101)

Currently `sync` requires a specific overlay name. Add `--all` to sync all applied overlays that have overlay-repo sources back to their repos. Natural complement to `update` which already supports all-overlay mode.

#### Already-applied indicator in pickers (#90)

When the interactive picker shows available overlays, already-applied ones should be visually marked or disabled. Prevents confusion and duplicate-apply errors.

#### `status --json` (#108)

Add structured JSON output to `status` for scripting and CI integration. At minimum `status --json` outputs applied overlay state (name, source, files, link types, applied_at). Consider `--quiet` for exit-code-only checks.

#### Interactive apply from browse (#109)

Allow users to select and apply overlays directly from `browse` in interactive mode. Makes `browse` the "discovery + apply" entry point. Non-interactive mode continues to just list overlays.

### Phase 3 — Breaking Changes

These are cleanup tasks that remove deprecated code paths. Done after features to avoid blocking feature work.

#### Remove legacy `overlay_repo` config (#79)

Drop the `overlay_repo` field from `RepoverlayConfig`, the `OverlayRepoConfig` struct, `needs_migration()`/`migrate_config()` functions, the legacy fallback in `resolve_three_part()`, and backwards-compat serialization. Users have had since v0.3.x to migrate.

#### Enforce `./` prefix for local paths

The codebase currently warns when a bare path (e.g. `my-overlay`) resolves as a local path instead of a structured reference. Turn the warning into an error — require `./my-overlay` for local paths to resolve ambiguity with `org/repo/name` references.

#### Remove deprecated commands

Remove commands that already show deprecation warnings:
- `create-local` (replaced by `create --output`)
- `add` (replaced by `edit --add`)
- `publish` (already hidden)
- `list` (replaced by `browse`)

### Phase 4 — Polish

#### Error message audit

Review all `bail!` calls (43 in lib.rs) and ensure error messages are actionable — suggest next steps, relevant commands, or common fixes. Remove all "in a future version" deprecation language since 1.0 is that version.

#### State format migration

Ensure that running 1.0 against a pre-1.0 state directory either auto-migrates gracefully or fails with a clear message explaining what to do.

#### Docs site content review

Fill in TODO sections from the docs site PR (#104). Ensure all 1.0 commands, flags, and workflows are documented.

### Phase 5 — Release

1. Final test pass across all features
2. Tag v1.0.0
